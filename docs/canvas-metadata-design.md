Candidate Canvas metadata collector
===================================

Status: implemented as an isolated, transport-free component in canvas-metadata.js.
It is not imported by the production Canvas client or enabled in the session gate.
Live guide refresh remains paused. This is a component of the replacement collector,
not a completed restoration of automatic collection.

Findings
--------

The review continues against upstream commit
`1c9f0bb8013ed69c4f2efe11fd483025469b7e6c`, not an identified UBC deployment.
GraphQL resolves selected fields separately, making a smaller read surface possible.
However, Assignment.description calls load_locked_for before processing its text.
Requesting that field would reintroduce the module lock path. PageType exposes a
title and todo date but no body in this revision. Neither API is a complete
replacement for the removed REST content reads.

The candidate's two fixed queries are:

- CanvasWeeklyAssignments: one chosen course, its ID/name/code and paginated
  assignment ID/course ID/name/state/points, overridden due/open/close dates and
  submission types. gradingPeriodId is explicitly null so future assignments are
  not silently limited to the current grading period. The scope defaults to the
  authenticated user; there is no configurable assignment user override.
- CanvasWeeklySubmissionStates: one course and one authenticated student ID,
  paginated submission ID/assignment ID/state. The states explicitly include
  unsubmitted and ungraded as well as submitted, pending_review and graded.
  Default GraphQL submission filtering would omit unsubmitted records. There are
  no answers, attempt contents, scores, comments or participant lists in this query.

Assignment dates use OverrideAssignmentLoader, which preloads override records and
calls overridden_for for the current user. Course submission scope intersects the
requested student IDs with those allowed by course permissions, then selects
existing Submission rows. Missing status data is not evidence of an unsubmitted
assignment: the future reconciliation adapter must preserve unknown status.

The [permission review](canvas-metadata-permissions-review.md) now traces course
permission preloading, override cloning/caches, visibility selection and the
controller's operation-name hooks. It identifies scoped-token incompatibility
and session CSRF requirements. Shared visibility/permission dependencies, model
load callbacks, schema analyzers and authenticated transport still require review
before the production gate is changed. This is not certification of the entire
request or institutional compatibility.

Contract and safeguards
-----------------------

metadataRequest constructs immutable request objects. permittedMetadataBody accepts
only their exact canonical JSON, bound to the selected course and authenticated
student. Extra variables/fields, alternative operation names, fragments, mutations,
duplicate JSON keys, multiple operations and expanded selections are rejected.
It must not become a generic GraphQL bridge or accept queries generated by AI.

parseMetadataPage rejects GraphQL errors even when some data is present, null or
wrong-course responses, malformed dates/IDs/status values, oversized page counts,
nonpublished assignments and inconsistent pagination. It copies only expected
fields, omitting unrequested content. Dates retain explicit null overrides; valid
zoned timestamps normalize to UTC. Invalid calendar dates fail instead of becoming
deadlines on another day.

collectMetadata has no default fetcher, URL, session or token. A caller must supply
the request function. It reads the two connections with independent cursors,
stops at 100 pages per connection, enforces 100 nodes per page, 2 MiB per decoded
response and 16 MiB total, and rejects repeated identities/cursors or ambiguous
statuses. Cancellation and failures reject the result rather than returning a
partial successful snapshot. Transport exception text and GraphQL errors are not
copied into user-visible errors.

The decoded-response budget is not a network allocation limit: the future
transport must enforce byte/time limits while receiving the body, before parsing.
A unit check exercises the existing production network guard to confirm that
POST /api/graphql is still denied; no live GraphQL request was made.

Validation for this milestone: both fixed queries pass GraphQL.js 16.11.0's schema
validator against the pinned upstream schema (SHA256
`19988080fe98cdb9e02d5a2df87043bcf18cef4e7f1714da2df3ebc090d03d13`).
That schema and a temporary validator are retained in ignored
.codex-temp/graphql-review for reproducibility, not shipped as dependencies.
Seven new unit tests exercise the body boundary, normalization, pagination,
failures, cancellation and limits. Schema validation proves field/type compatibility
for that revision, not resolver side-effect freedom or UBC compatibility.

Integration work still required
-------------------------------

1. Finish the permission/override/controller review described above.
2. Add a named authenticated transport for only these exact bodies, with bounded
   reads, manual redirects, cancellation and flushed intent/outcome audit. Bind
   pending network admission to method, origin, body and authenticated identity;
   a browser must not borrow a pending request. Session CSRF and API-token paths
   need separate verification. Scoped developer-key tokens cannot access the
   required GraphQL types in the reviewed revision; report this without asking
   for broader permissions. GraphQL uses POST, so method alone cannot enforce
   the mutation boundary. Apply the additional identity, envelope and CSRF checks
   recorded in the permission review.
3. Merge fresh metadata with saved instructions without erasing them or claiming
   that their contents were refreshed. Display field-specific age and source gaps.
   Match status records only to the current assignment list; an absent status row
   remains unknown, and unmatched rows must not invent assignments.
   Keep quiz-only metadata and course materials coverage explicit. A partial
   metadata stage must not be presented as the full collection objective achieved.
4. Restore useful automatic collection only after the complete supported path is
   reviewed and tested. Continue work on course instructions, messages, external
   websites and documents through permitted sources; do not loosen the student's
   no-assessment/no-learning-state-write boundary to fill gaps.
5. Validate institutional schema, authentication, student-specific dates and
   pagination with the authorized account once the read path is established.
   Never use an unreviewed live request to discover whether it changes state.
